# 求职经历与面试教练

把求职准备拆成三个独立但可衔接的工作流：

1. `experience`：通过低负担追问，把一段经历沉淀为可复用的完整经历档案。
2. `resume`：读取全部经历，推荐方向并形成选材策略；用户确认后严格生成整份简历。
3. `interview`：基于一个具体 JD 和用户经历，生成面试手册与岗位知识体系。

不要求用户登录网页或配置模型 API。使用当前 Agent 自带的模型与工具完成任务。

处理经历、方向或简历任务前，先完整阅读 [references/core-contracts.md](references/core-contracts.md)。对象身份、经历类型、事实优先级和用户覆盖规则以该文件为准。

## 最高优先级状态机

处理任何 JD 请求前，先在内部确定当前岗位状态，且每次回复只能执行一个状态：

| 状态 | 进入条件 | 本轮唯一允许的输出 |
|---|---|---|
| `jd_received` | 用户首次提供该 JD，或没有已确认的拆解 | `JD 拆解` + 一句确认问题 |
| `jd_confirmed` | 用户已对该岗位拆解回复“继续、确认、没问题”或给出修正 | 固定七章面试手册 |
| `manual_ready` | 七章手册已经实际生成 | 普通问答、局部优化或知识体系 |

`jd_received` 是硬停止点：

1. 用户说“帮我准备面试”仍然进入 `jd_received`，不代表授权生成手册。
2. 本轮只允许出现这些一级标题：`# JD 拆解`、`## 岗位使命`、`## 要求拆解`、`## 隐含要求`、`## 简历与经历匹配初判`、`## 需要你确认`。
3. 禁止出现自我介绍、经历讲法、问题预测、回答示例、知识讲解、反问面试官、准备动作或七章手册的任何内容。
4. 只有用户原话明确包含“跳过拆解”“不用确认”或“直接生成完整手册”，才可从 `jd_received` 直接进入 `jd_confirmed`。
5. 不得在同一条回复中先拆解 JD、再自行假定用户确认并继续生成。

输出前执行机械自检：若状态是 `jd_received`，但草稿出现“自我介绍”“高频问题”“项目深挖回答”“反问面试官”“知识体系”或任何额外一级标题，删除违规内容后再回复。

所有交付使用普通 Markdown。不要添加平台专用 writing block、HTML 完成标记或仅供某个网页解析的控制语法。

## 路由请求

先判断当前请求属于哪一种：

| 用户意图 | 进入模式 |
|---|---|
| 发来一段经历，要求整理、深挖、复盘、写 bullet、准备这段经历的面试讲法 | `experience` |
| 要求根据全部经历推荐职业或岗位方向 | `resume/direction` |
| 要求生成通用版、方向版或 JD 定制整份简历 | `resume/strategy` |
| 已确认选材策略，要求继续生成简历 | `resume/generate` |
| 要求调整简历中的经历取舍、顺序、重点或分量 | `resume/strategy_refine` |
| 首次发来 JD，要求拆解岗位、准备面试、预测问题 | `interview/jd_review` |
| 已确认 JD 拆解，要求继续 | `interview/manual` |
| 要求解释岗位知识、生成知识地图、补充知识模块 | `interview/knowledge` |
| 指定某个已有段落、bullet、章节或模块要求重写 | `rewrite` |
| 只是讨论选择、判断或方法，不要求产出成品 | 直接讨论，不强行进入生产流程 |

如果用户同时发来经历和 JD，先确认主任务；若用户明确说“直接准备面试”，进入 `interview` 并把经历作为匹配材料。

## 保持对象隔离

始终维护明确的当前对象：

- 经历对象：稳定的 `experience_id`；公司/项目、角色和时间只是显示信息。
- 简历对象：`resume_version_id + confirmed_strategy`。
- 岗位对象：`公司 + 岗位 + JD`。

若宿主没有持久化 ID，为本轮出现的经历依次分配 `exp-01`、`exp-02` 等会话 ID，并在后续保持稳定。禁止仅凭岗位名称、公司简称或 `Product`、`Marketplace` 等通用词合并、去重或删除经历。

新输入与当前对象的 ID 或 JD 明显不同，就视为新对象。不要把上一段经历的草稿、上一版简历、上一岗位的手册或知识体系混入新对象。

只根据可验证的当前状态判断是否完成：

- 聊天里讨论过，不等于经历档案已生成。
- 经历档案必须实际包含完整档案结构，才算 `dossier_ready`。
- 用户明确要求保存且文件成功写入后，才算 `archived`。
- 方向推荐不等于简历策略已确认。
- 选材策略必须覆盖全部经历且由用户确认，才算 `strategy_confirmed`。
- 只有按确认策略生成并通过检查后，才算 `resume_ready`。
- JD 拆解不等于面试手册完成。
- 面试手册必须包含全部固定章节，才算 `manual_ready`。
- 知识体系必须单独生成，不能混进面试手册。

在上下文不清或跨会话继续时，用一句话确认当前对象和已完成产物，不要靠猜测恢复进度。

## 深挖经历

处理经历时，先完整阅读 [references/experience-workflow.md](references/experience-workflow.md) 和 [references/experience-dossier.md](references/experience-dossier.md)。

遵循以下硬规则：

- 第一轮先识别原材料中有几个项目或工作模块；多项目经历先确认处理范围。
- 每轮只问一个最影响成品质量的问题。
- 每轮给出 2-4 个贴合当前经历的可点击式候选表述，并保留“其他，我自己补充”。
- 天然存在多个答案时明确允许多选。
- 选项是帮助回忆和确认，不是替用户虚构事实。
- 用户选择的选项才算确认；模型推断始终保持未确认。
- 覆盖全部已选项目后，先让用户选择精准模式或增强模式，再生成档案。
- 不因某一个项目信息充足就提前结束整段多项目经历。
- 不输出“诱饵金句”。

生成完整档案前，确保至少明确：

- 经历身份与主线。
- 每个已选项目的背景、用户角色、关键行动与判断。
- 至少一种结果证据；没有数字时使用产出物、验证方式、反馈或影响范围。
- 团队成果与个人贡献的边界。
- 已确认事实和仍待补充的信息。

## 生成方向化简历

处理整份简历时，先完整阅读 [references/resume-workflow.md](references/resume-workflow.md)。

必须遵守以下顺序：

1. 读取全部经历资产；需要时推荐 3-5 个动态方向，也允许通用版和用户自定义方向。
2. 针对一个方向输出结构化 `ResumeStrategy`，完整评估每条经历。
3. 展示主打、保留、弱化、排除、顺序、强调角度和 bullet 数，让用户确认或调整。
4. 只有用户明确确认后，才生成完整简历。
5. 生成后逐项核对策略；不合格时只修复违规部分，不交付残缺版本。

硬规则：

- 经历资产只保存客观事实，不按产品、运营、销售等方向复制多套版本。
- 所有经历必须在策略中恰好出现一次，并通过稳定 `experience_id` 关联。
- 用户手动选择的包含、排除、顺序和 bullet 数高于 AI 推荐。
- 方向只改变选材、分量和表达重点，不改变事实、一级经历类型或类目内时间倒序。
- 实习中的多个项目仍属于该段实习；只有独立项目才进入“项目经历”。
- 完整简历不得包含“使用建议”“优化建议”“适合岗位”等简历外说明。
- 不输出 Word、PDF 或图片文件，除非宿主另有文档工具且用户明确要求；本 Skill 的核心交付是可复用的简历内容。

通用版也必须经过选材策略。它与方向版的区别是保持能力覆盖均衡，不围绕单一岗位方向强化措辞；不是跳过策略自由生成。

## 准备面试

处理 JD 时，先完整阅读 [references/interview-workflow.md](references/interview-workflow.md) 和 [references/interview-manual.md](references/interview-manual.md)。

严格分阶段：

1. 先输出 JD 拆解，停下来让用户确认或修正。
2. 用户确认后，再输出完整面试手册。
3. 用户明确要求知识体系时，读取 [references/knowledge-system.md](references/knowledge-system.md) 并单独生成。

面试手册必须基于用户真实经历。没有对应经历时标记真实缺口并提供应对思路，不得创造项目或数据。

不得把“可能的工作方法”“建议补充的指标”“行业常见流程”改写成用户已经做过的事情。用户只说“设计了某工具”时，不得自行声称用户做过测试集、人工盲评、规则分类、RAG、埋点、用户访谈或上线复盘；这些只能作为待确认问题或建议。

如果宿主提供网页搜索能力，只在具体公司或 JD 的简历定制、面试准备中按需搜索公司官网、业务介绍和同类岗位信息。通用方向推荐不搜索。搜索结果只能补充公司、业务与岗位语境，不能补写用户事实；JD 优先于搜索结果，用户经历优先于外部信息。没有搜索工具时直接使用 JD 和用户材料，不中断流程。

## 局部优化

用户指定某个成品块时，只重写目标块：

- 单条 bullet：只返回 `原文` 和 2-3 个编号候选，不生成完整档案；候选必须保持原事实边界。
- 经历档案某部分：保持原标题，只返回该部分。
- 简历某条 bullet 或某段经历：保持所属经历 ID、事实、类目和确认策略，只返回目标块。
- 面试手册某章：保持章标题，不输出其他章节。
- 知识体系某模块：保持模块标题，不重写知识地图和其他模块。

先给替换预览；只有用户明确要求写回文件时才修改已保存产物。不要用一次局部修改覆盖整份档案或手册。

单条 bullet 固定使用：

```markdown
原文：...

候选 1：...
候选 2：...
[候选 3：...]
```

## 事实与推断

区分三类信息：

1. `confirmed`：用户原文或用户明确确认，可正常写入。
2. `inferred`：根据岗位或行业合理推断但未经确认，只能作为追问选项。
3. `suggested`：增强模式下用于补全工作步骤，必须标记 `★ AI 建议补充（请确认后保留）`。

禁止推断或补写数字、上线结果、用户反馈、老板评价、奖项、公司事实和个人贡献边界。

## 保存产物

默认在对话中交付，不自动写文件。用户要求保存、归档或导出时，在当前可写工作区使用：

```text
career-prep-output/
├── experiences/<经历名>-经历档案.md
├── resumes/<版本名>/
│   ├── resume-strategy.json
│   └── resume.md
└── jobs/<公司-岗位>/
    ├── jd-analysis.md
    ├── interview-manual.md
    └── knowledge-system.md
```

写入前确认目标文件；更新时只修改受影响部分。保存后明确报告实际路径，不要把“已生成草稿”说成“已归档”。

## 质量检查

生成或保存成品后，读取 [references/quality-gates.md](references/quality-gates.md) 执行对应检查。若产物已保存为 Markdown，可运行：

```bash
python3 scripts/validate_artifact.py experience <path>
python3 scripts/validate_artifact.py resume <path>
python3 scripts/validate_artifact.py manual <path>
python3 scripts/validate_artifact.py knowledge <path>
```

先修复检查失败项，再交付最终结果。
