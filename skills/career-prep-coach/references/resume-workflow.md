# 方向化简历工作流

## 1. 总体流程

```text
全部经历资产
  ↓
动态方向推荐或用户自定义方向
  ↓
结构化选材策略
  ↓ 用户调整并明确确认
严格生成完整简历
  ↓
策略一致性检查与局部修复
```

经历资产保持唯一、客观。职业倾向只存在于选材策略和简历版本中。

## 2. 输入准备

开始前整理：

- 全部经历及稳定 `experience_id`。
- 教育背景、联系方式等基础信息。
- 用户选择的简历模块。
- 目标模式：`baseline`、`direction` 或 `jd`。
- 方向名称；JD 模式还需要具体 JD。

缺少经历 ID 时先分配会话 ID。不要要求用户先手动勾选经历，AI 应先完整评估全部经历。

## 3. 动态方向推荐

用户未明确方向时，基于全部经历推荐 3-5 个方向。推荐依据优先读取：

1. 用户真实完成的动作与结果。
2. 可迁移能力和问题解决方式。
3. 多段经历重复出现的能力证据。
4. 历史岗位名称。

历史 title 只能作为弱证据，不能直接把过往职位列表改写成推荐结果。

每个方向输出：

```json
{
  "label": "方向名称",
  "fit": "strong | medium | exploratory",
  "reason": "为什么匹配",
  "evidenceExperienceIds": ["exp-01", "exp-03"],
  "coreCapabilities": ["能力一", "能力二"],
  "gaps": ["真实短板"]
}
```

同时提供：

- `通用版本`：保持能力覆盖均衡。
- `自定义方向`：用户可直接输入，不需要从推荐项中选择。

通用方向推荐不调用网页搜索。

## 4. 结构化选材策略

每次只为一个目标生成一份策略。必须使用以下结构：

```json
{
  "target": {
    "label": "B端解决方案",
    "source": "recommended | custom | jd",
    "mode": "baseline | direction | jd"
  },
  "positioning": "这版简历要呈现的候选人定位",
  "competencySignals": ["客户需求理解", "复杂流程拆解", "方案交付"],
  "keywords": ["解决方案", "业务流程", "多角色协同"],
  "experiencePlan": [
    {
      "experienceId": "exp-01",
      "treatment": "lead | include | deemphasize | exclude",
      "order": 1,
      "angle": "本次重点强调的能力与内容",
      "bulletCount": 3,
      "reason": "为什么这样处理",
      "userOverride": false
    }
  ],
  "evidenceGaps": ["具体经历及待补信息"],
  "generationConstraints": ["生成时必须遵守的约束"]
}
```

策略硬校验：

- 全部经历在 `experiencePlan` 中恰好出现一次。
- `experienceId` 必须存在，不能用标题替代。
- `lead`、`include`、`deemphasize` 才进入简历；`exclude` 不得出现。
- 实际使用的经历必须有唯一顺序。
- 每段 `bulletCount` 为 1-4。
- `angle` 必须能被该经历的已确认事实支撑。
- `evidenceGaps` 只列缺口，不能作为已发生事实。
- 用户改过的项目设置 `userOverride: true`，后续 AI 不得自动覆盖。

若结构解析失败、经历漏评、ID 不存在或字段不完整，自动修复一次。仍失败时停止在策略阶段，不生成简历。

## 5. 用户确认门

展示策略时使用清晰的可读摘要，而不是只抛出 JSON。至少展示：

- 当前定位。
- 每段经历的处理方式。
- 简历内顺序。
- 强调角度。
- bullet 数。
- 证据缺口。

允许用户调整包含关系、顺序、角度和 bullet 数。每次调整后更新同一份结构化策略。

只有用户明确表达“确认策略”“按这个生成”等含义后，状态才进入 `strategy_confirmed`。不能把用户选择方向视为确认策略，也不能在同一回复中默认确认并生成。

## 6. 严格生成

完整简历生成必须接收 `confirmedStrategy`，不能只收到一个方向名称后自由发挥。

生成规则：

- 事实只能来自对应经历资产中的 `confirmed` 内容。
- 只生成策略中非 `exclude` 的经历。
- 不遗漏用户手动包含的经历。
- 每段经历的分量和 bullet 数严格符合策略。
- 一级栏目由经历类型决定；实习内部项目不能移到项目经历。
- 每个一级栏目内部按时间倒序，不因策略改变。
- 方向改变的是动作选择、信息密度和措辞重点，不改变事实。
- 没有真实内容的可选栏目直接省略。
- 不输出简历使用建议、岗位建议、解释、完成标记或策略分析。

默认使用清晰 Markdown：

```markdown
# 姓名

联系方式

## 教育背景

### 学校｜专业 学位｜时间
[补充信息]

## 实习经历

### 公司｜角色｜时间
- ...

## 项目经历

### 项目｜角色｜时间
- ...
```

栏目按用户配置决定；常见可选栏目包括个人介绍、技能、校园经历和获奖成就。正文中不要输出经历 ID。

## 7. 三种版本

- `baseline`：能力覆盖均衡，适合尚未明确方向时使用；仍需完整策略。
- `direction`：围绕一个职业方向调整经历分量、强调角度和关键词。
- `jd`：在方向版或全部资产基础上，围绕具体 JD 重新生成并确认策略。

JD 定制不能覆盖原方向版。若需要保存文件，为每个版本建立独立目录。

## 8. 生成后检查与修复

逐项核对：

- 确认使用的经历是否全部出现。
- 被排除的经历是否消失。
- 每段经历是否映射到正确 ID，且只出现一次。
- 一级栏目归属是否正确。
- 栏目内是否按时间倒序。
- bullet 数是否符合策略。
- 是否出现未确认事实或外部信息冒充个人事实。
- 是否混入简历外建议。

发现遗漏时，根据缺失 `experience_id` 只生成对应经历块并插回正确栏目和时间位置，不要整份自由重写。发现重复时按 ID 定位重复块，不使用标题模糊去重。

自动修复一次后仍不合格，保留原稿并明确指出未通过项，不交付残缺版本。

## 9. 局部调整

生成后可以：

- 修改单条 bullet。
- 重写某段经历。
- 调整某段经历分量。
- 修改策略后生成新版本。

局部重写必须保持经历 ID、类型、事实和当前定位。若用户修改的是包含关系、顺序、角度或 bullet 数，先更新策略，再重新生成受影响的经历块；不要让局部改写暗中改变整份简历选材。
